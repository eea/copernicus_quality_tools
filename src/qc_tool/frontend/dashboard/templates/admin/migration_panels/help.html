Creating a new migration

A developer creates migration files with a model or data change, reviews them and ships them with a QC Tool release. As administrator, you apply that installed plan through this page.

  1. Develop and review. Generate native Django migrations in development, commit them with the change and test the supported upgrade paths on disposable copies.
  2. Install the reviewed release. The deployment operator installs the matching frontend and worker images under maintenance. New pending migrations then appear here.
  3. Apply through a verified copy. Pause work, create a complete backup, prepare and verify a copy, then explicitly switch. Finish checks before reopening.

A release with no schema or data migration reuses the existing history. The version number alone does not require a database update.

Schema drift, missing history or database unavailable

Keep maintenance on and preserve the source, backup and operation journals. Read the specific blockers above; an unexpected schema is not an ordinary pending migration.

The deployment operator can run the read-only whole-application database plan and database check commands to investigate. Have the release maintainer review unsupported differences before continuing. Do not reset tables, fake migration history or edit applied migration files to bypass a blocker.

Interrupted upgrade or failed verification

Open the upgrade attempt above. Use Verify and retry only when the server offers it. If migration execution is uncertain, retain the failed copy and stop the upgrade through the guarded action; then prepare a fresh copy from a verified backup.

Preparation continues in the background if you leave this page. A lost browser connection is not proof that the migration stopped or rolled back. Keep maintenance on until the operation is complete or recovered.

Delivery files, storage compatibility & rollback

Migration preparation retains the original database and shared delivery archives, specifications, boundaries, QC outputs and publications at their existing paths. Review file coverage and missing or external content in the backup and candidate checks. Keep an independent recovery copy outside the runtime storage.

A database migration does not relocate or convert files. A future storage-format change needs its own reviewed procedure. Reversing a schema migration does not recover discarded data or files.

Quick switch-back is limited to the same maintenance window before normal work resumes. Once new work has been accepted, an older database can lose that work. Recovery may require the previous pinned application images and an offline operator procedure.
