## Change and compatibility

- The initial migrations create the reviewed application tables, constraints
  and indexes. Django applies its own auth, content-type, admin and session
  history through the same whole-application command. Neither baseline imports
  data, creates products, rewrites specifications or fetches external resources.
- Keep both baseline files and the policy mapping immutable. Subsequent schema
  changes require forward migrations, including future major versions.
- Default users and product managers use explicit product assignments. Product
  plans, required units, review decisions and final manager confirmation govern
  readiness. Successful QC or a historical submission date does not imply an
  accepted current submission.
- Legacy profile/country/region authorization and old API credentials are not
  restored. S3 sources are retained without secrets. Review permissions and
  replace credentials explicitly before permitting production use.
- Uploaded specifications remain byte-for-byte unchanged. An empty installation
  has no catalog products until administrator upload or an explicit reviewed import.
- The source SQL dump has no delivery ZIPs, reports or published folders. Preserve
  recoverable records and dates, but do not claim restored downloads, verified
  receipts, approvals or completed products.
- Old application images are not supported against the frozen schema. Deploy a
  frontend/worker pair verified for this release. Do not attach a legacy or
  model-created draft database to the new frontend, and do not fake migrations.
- PostgreSQL migrations use Django's migration transactions and the application's
  advisory deployment lock. There is no single transaction spanning the release.
  The legacy import is a separate transaction into an otherwise fresh target.

## Deferred deployment and recovery

No production database, services, storage or traffic were changed. Before
deployment, complete the site-specific fields above and the
[deployment record template](../RELEASE_TEMPLATE.md). The operator must supply:

- A new target database and storage volumes, image digests, secret references,
  environment lock owner, and an explicit maintenance window.
- Confirmation that the 20260907 dump is the intended source snapshot and an
  account of any later legacy writes. Preserve the original dump and verified
  backups; storage is unavailable for this source.
- The exact plan/apply/check and import commands, reviewed access mapping,
  restored credential references, data reconciliation and stop conditions.
- Login and denied-access checks; representative upload and actual worker QC;
  publication, individual/bulk review and final manager readiness checks.
- A rehearsed target restore, monitoring thresholds and recovery window. Keep
  the old installation offline after switching traffic. Returning to the old
  deployment after new writes requires explicit data reconciliation; changing
  application images alone is not a database rollback.

Follow [manual cutover](../MIGRATIONS.md#one-time-manual-production-cutover) and
[legacy import](../LEGACY_IMPORT.md). Never restore the old SQL schema over the
new target or reset a developer database to simulate the cutover.
