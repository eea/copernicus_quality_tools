# QC Tool 3.0.0 release record

## Current schema contract

QC Tool 3.0.0 uses `policy.json` phase **`draft`**, with an empty `baselines`
mapping. It ships no first-party migration definitions or schema snapshots.
Django models own the schema created in a fresh target by the whole-application
`database plan|apply|check` command. Initialization does not alter existing
columns, indexes or constraints, import products, or reset a database.

Initial migration history may be introduced only by a separately reviewed
release in **3.0.1 or later**. That future freeze is not an automatic upgrade of
model-created 3.0.0 databases. Review a fresh-target conversion or explicitly
approved adoption design first; do not fake or rewrite migration records.

The source correction retains the Delivery model's nonunique conditional
`LOWER(filename)` index for submitted-history lookups. It does not modify
original product specifications, uploaded specification snapshots or protected
raster/vector checks. No existing database or production deployment is changed
by removing the superseded unpublished schema definitions from this branch.

## Corrected source verification: 2026-10-13

An isolated fresh PostgreSQL target initialized directly from current models
passed schema, role, repeated-initialization and declared-index checks, plus
**103 focused regression tests**. Read-only inventory measured **23 tables,
189 columns, 119 constraints and 91 indexes**. The migration recorder is absent,
there are no applied migrations, and there are no first-party migration
definitions in the source. The three automatic auth membership-table row IDs
are `integer`. Existing databases were not touched.

The fresh SQLite target also passed schema checks: **103 tests collected,
100 passed and 3 PostgreSQL-only skips**. It has 23 tables and 189 columns, no
migration recorder/history, and an empty catalog/user inventory before fixtures.
All 17 focused history/upload tests passed. Both temporary runtimes were removed;
protected QC source remained unchanged. The final committed source identifier
must be recorded after review. These checks do not certify the full frontend
suite, worker parity, packaged images, or production readiness.

The host checks also passed: **31 migration-policy/history tests**, **41 offline
maintainer-tool tests**, the exact unpublished-correction guard against
`41a1427f47ce8e8068ac6605d6bc17377309a69c`, workflow validation and local
documentation links. The guard rejects any v3.0.0 migration-managed policy and
requires the committed correction audit to remain unchanged on later comparisons.

## Evidence boundaries

Local available-history conversion is distinct from a coherent production
snapshot. Web-admin exports and older SQL data do not establish complete current
password, storage or QC-result coverage. Historical submission dates retain
history and duplicate-admission information; they do not manufacture approvals,
publication receipts, content hashes or completed catalog coverage.

Worker verification used original captured inputs/specifications in isolated
runtimes. Its current-check samples do not all match archived production reports;
those reports are historical stored outcomes, not new executions on today's
production. The damaged-ZIP exception does not authorize other acceptance
changes. See the [parity evidence guide](../../../../docs/development/legacy-qc-parity.md).

Earlier frozen-candidate source/artifact checks are retained in Git history but
are superseded for this release policy. Their migration graph and packaged
image cannot be relabelled as verification of the models-only candidate. This
record does not claim that those earlier databases were reset or adopted.

## Operator follow-up

Read the [database guide](../README.md), [runbook](../MIGRATIONS.md),
[legacy importer](../LEGACY_IMPORT.md) and [release template](../RELEASE_TEMPLATE.md)
from the exact source selected for the artifact. Preserve existing users and data
before choosing any new development target. Do not initialize a released graph
against an existing models-only database, fake a baseline, or restore legacy DDL
over a new target schema. Storage, credentials, production authorization,
coordinated write stop, restore rehearsal and a recovery window remain explicit
operator responsibilities.
