# QC Tool 3.0.0 migration management

## Release contract

The current 3.0.0 includes committed first-party Django migrations and an
explicit candidate-only adoption procedure for the supported history-free schema
of earlier 3.0.0 installations. The application version remains 3.0.0; a version
label alone does not establish whether migration history exists or whether an
earlier draft database has the supported schema. The dated
[models-only installation record](3.0.0-models-only.md) is preserved unchanged.
Future 3.0.1 and 3.1.0 releases preserve this history and add reviewed forward
migrations.

The installed [policy](../policy.json) owns the reviewed adoption targets.
Django framework migrations and the `accounts`, `dashboard` and `qc_database`
initial migrations define one application schema. Later releases preserve their
identities and add reviewed forward migrations.

## Operational behavior

Fresh SQLite/PostgreSQL installations use committed migrations through explicit
empty-target `database apply`. Repeat application leaves a current managed
database unchanged. Startup checks readiness without applying pending history.

Admin upgrades require ready maintenance, a verified native PostgreSQL backup
with retained file coverage, a separate operation-owned restored candidate,
strict supported-source checks, native forward migrations, target/storage/access
verification and an explicit switch. The serving database is not migrated in
place. Previous database, backup, candidate, journals and shared-file pins remain;
cleanup and reopening are never automatic.

Original specifications and snapshots are never rewritten. SQL migration does
not move ZIPs, QC results, boundaries or publications. Private configuration and
global SQL remain inert recovery material. Remote objects and arbitrary host
state need independent coordinated backup.

Minor `3.0.x` and major `3.x.0` labels do not determine compatibility. Source
contracts, committed history and storage behavior do. Unknown earlier draft
schemas are refused. Across incompatible schemas, recovery needs the previous
pinned images and retained data under an offline procedure.

## Verification record

The current 3.0.0 frontend and worker were subsequently rebuilt from the
`release/v3.0.0` checkout and deployed locally on 2026-11-06. A verified full
backup was copied outside the runtime volumes. History initialization ran on a
separately restored PostgreSQL candidate, which was explicitly selected after
verification. All three existing accounts were preserved; the retained original
database's native fingerprint remained unchanged. The active candidate reported
21 applied migrations and none pending. Maintenance was explicitly turned off,
and authenticated HTTP requests to the migration page and workspace returned
200. Both running application images reported version 3.0.0.

This current-version build passed 191 PostgreSQL regression tests, the model
drift gate and a fresh-schema initialization probe. A separate nine-test
PostgreSQL batch covered database selection and a regression found during the
local rollout: isolated candidate connections must inherit Django-normalized
connection defaults, including `TIME_ZONE`, even when operator configuration
omits them. The initial attempt stopped before any migration began; retry after
the correction completed successfully. Credential-bearing rollout evidence and
recovery material remain outside Git. These local checks do not establish an
EEA/Rancher or production deployment.

Local verification on 2026-11-06 used disposable databases and the pinned
Python 3.12 / Django 5.2.17 frontend runtime, with PostgreSQL 17. Those regression snapshots used the local
`qc-tool-frontend:migrations-review` image before the release-label correction,
when its metadata identified version 3.0.1 and source revision `uncommitted`.
That metadata is historical test provenance, not a released 3.0.1 or evidence
that the current 3.0.0 image has been rebuilt or deployed.

- A packaged full regression snapshot passed **2,507 tests on PostgreSQL 17
  (one skip)** and **2,507 tests on SQLite (73 backend-specific skips)**.
- A refreshed image passed **319 focused PostgreSQL tests** and
  **319 SQLite tests (44 backend-specific skips)**.
  This final batch covers schema/history guards, backups, retained file pins,
  candidate upgrades, selection, recovery, authentication, Admin and maintenance.
- Enforced read-only inspection of the serving 3.0.0 schema exposed an omitted
  supported variant: three implicit Django auth join IDs were `integer` rather
  than `bigint`. Recognition now accepts either known width only on those three
  columns. The latest image passed **104 PostgreSQL core, upgrade, recovery and
  Admin tests** after that correction. Both source variants adopt without width
  changes; `smallint` join IDs and an incorrect business-model ID width remain
  refused. The serving-schema recheck reported a supported history-free 3.0.0
  source with no schema problems and 21 pending migration identities. It used
  PostgreSQL read-only connection options plus a query guard; no serving
  database migration or storage operation was performed.
- Real Admin HTTP tests used CSRF-protected forms and PostgreSQL for backup
  review, preparation, verification and explicit selection. A selected database
  made unavailable still admitted retained-source authentication and displayed
  the operation journal with unsafe actions disabled. Seven desktop/mobile
  fixture states were visually checked; the separate focused UI batch passed
  112 tests.
- Missing dependencies, cycles, conflicting graph branches and invalid historical
  model bases produce read-only blockers. Current model changes without committed
  migrations cannot appear ready. Native database defaults/generated columns
  are compared with Django-compiled expressions; declared changes pass and
  unexpected physical expression changes are refused.
- Storage validation binds both available content and configured absolute roots,
  including empty roots. Identical physical specification aliases receive one
  retained pin; conflicting evidence is refused. A stopped operation without its
  maintenance pin cannot be retried through a forged recovery request.
- Real PostgreSQL forward-upgrade fixtures applied `AddField` and `RunPython`
  to a managed candidate, verified a receipt and explicitly selected it while
  preserving source schema/data and original files. A migration introducing a
  missing ZIP reference was blocked before completion/selection. Temporary
  migration packages, runtime fields and transfer-registry extensions were
  removed after each test; no future migration definitions are shipped.
- Native fresh initialization, role bootstrap, synthetic-row preservation and
  read-only repeat application passed on SQLite and PostgreSQL. The model drift
  gate, source policy, Django checks, static collection and production deployment
  checks passed. All **270 JavaScript tests** passed; four standalone Compose
  profiles passed configuration validation.
- Desktop and 320/390px Admin screens were visually reviewed using fixture
  operation data. Real migration execution was verified separately on PostgreSQL.

The complete regression snapshot preceded the final diagnostic guard for
unrenderable historical model bases and the auth join-width compatibility
correction. The 319-test batch includes the diagnostic guard; the latest
104-test batch includes both corrections. No production database was reset or migrated. These checks do not
establish EEA/Rancher deployment, distributed-storage behavior, a production
restore, a release tag or a production cutover. Follow the
[release template](../RELEASE_TEMPLATE.md) for each installation and retain
credential-bearing evidence outside Git.
