Environment configuration
=========================

Use docs/reference/environment-variables.md for the maintained variable names,
defaults and validation rules. Application defaults belong in Python:
  * src/qc_tool/storage/layout.py owns configured runtime paths;
  * src/qc_tool/common.py owns shared application configuration;
  * src/qc_tool/frontend/settings.py adapts frontend settings and typed limits;
  * worker/security packages own their validated execution limits.
Do not copy advanced default lists into each Compose entrypoint.

Standalone Compose profiles
---------------------------

Each maintained profile is one complete Compose file containing its services,
mounts, connectivity, health checks and role-specific environment passthrough.
Choose exactly one for a deployment:
  * docker/compose.local.yaml: local builds and source mounts;
  * docker/docker-compose.eea.yml: production PostgreSQL with named volumes;
  * docker/compose.eea-storage.yaml: complete Azure/EEA host-storage deployment;
  * docker/docker-compose.service_provider.yml: SQLite/lightweight validator.

The host-storage file is selected alone, not merged with the named-volume EEA
file. Download the selected production file from the reviewed source revision.
No shared Compose import, generator, wrapper or exported manifest is required.
Use current supported Docker Compose. A standalone definition does not certify
compatibility with a particular Rancher importer: verify its actual version,
deployment type, supported schema and environment/secret handling on the target.

Protect operator settings in a file outside the checkout, such as private.env,
and pass it with docker compose --env-file, or use the deployment platform's
reviewed configuration/secrets mechanism. This supplies deployment values,
not another Compose file or blanket container environment injection. Only
variables explicitly passed in a role's service configuration reach that
container. Review that profile's passthrough before relying on an override;
frontend secrets must not be passed to workers. Avoid sharing rendered
configuration containing secrets.

Filesystem and persistence
--------------------------

All application paths describe the container filesystem. Host bind sources are
separate operator configuration; equal container paths can have different
frontend/worker sources, as with their private log volumes.

Maintained profiles select QC_TOOL_DATA_ROOT=/mnt/qc-tool/data and separately
mount data, shared control state, frontend-private state, worker scratch and
role-specific logs. Workers read incoming deliveries, specifications and
boundaries through read-only mounts. Jobs and shared state are writable;
submissions and frontend-private state are absent. Preserve those boundaries.

See docs/architecture/runtime-storage.md for directory ownership and lifetimes,
and docs/deployment/eea-storage.md for host provisioning, mount/identity checks
and the explicit fresh-target handoff. Startup validates mounted roots before
application writes; it never repairs missing mounts, moves old volumes, adopts
older data or upgrades an occupied database. PostgreSQL 17 uses a fresh
volume/path and must never open an old PostgreSQL 14 cluster directory.

Database initialization remains the whole-application database plan|check|apply
workflow. A completely matching schema is read-only; an entirely empty target
can be explicitly initialized; partial/foreign/outdated schemas are refused.
Read src/qc_tool/database/README.md before persistence or deployment changes.

Debugging scratch
-----------------

LEAVE_SCHEMA=yes retains the worker job schema for investigation.
LEAVE_JOBDIR=yes intentionally retains worker scratch; retained reports/results
are independent. Explicit scratch cleanup respects that debugging marker,
active leases and process namespaces. It is not a general storage TTL policy.
